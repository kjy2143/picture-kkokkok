# 틀린그림찾기 제작 품질 가이드

그림콕콕의 새 게임 제작과 기존 그림 수정에 적용한다. 제작자는 원본을 확인한 뒤 차이를 계획하고, 생성한 그림과 실제 플레이를 각각 검수한다. 사용자가 지정한 주제·비율·수정 범위를 우선한다.

파일 형식과 명령은 [CONTENT.md](CONTENT.md), 제품 요구사항은 [PRD.md](PRD.md)를 따른다. 이 문서의 차이 배분은 제작 기본 기준이다. 아이의 체감 난이도는 실제 플레이로 확인한다.

## 1. 장면과 화면 비율

- 선명한 윤곽, 또렷한 색, 친근한 동화책 일러스트를 사용한다. 텍스트·로고·워터마크·정답 표시를 넣지 않는다.
- 장면의 주인공과 주변 사물을 구분할 수 있게 구성한다. 차이를 넣을 대상은 화면 위·가운데·아래에 분산한다.
- 2026-10-15 사용자 정정에 따라 iPad 가로 모드에서 좌우 비교할 그림은 4:5 세로를 기본으로 한다. 기본 해상도는 1120×1400이며 사용자 지정 비율을 우선한다. 비율과 해상도를 생성 계획에 명시한다.
- 원본과 변경 그림은 같은 비율·해상도·구도·프레이밍을 사용한다. 정답 대상이 잘리거나 한쪽에서 가려지면 안 된다.
- 기존 게임의 비율이나 구성을 작업 범위 밖에서 바꾸지 않는다. 기존 가로 게임 18개를 4:5로 재생성했다. 세로 시범 ‘키 큰 나무 아래 소풍’은 2026-10-28 사용자 요청으로 목록에서 제거했다.

## 2. 차이 유형을 섞는다

색깔 차이도 허용한다. 색깔만 반복하거나 모든 차이를 모양 변경으로 만드는 구성을 피한다. 각 차이에 주 유형 하나를 기록한다.

| 유형 | 예시                            | 계획할 때 확인할 점                                                    |
| ---- | ------------------------------- | ---------------------------------------------------------------------- |
| 색깔 | 빨간 사과 ↔ 초록 사과           | 사과 모양·위치는 유지한다. 색깔만 바뀌는 차이는 기본 1~2개로 제한한다. |
| 표정 | 입을 벌린 웃음 ↔ 입을 다문 웃음 | 눈·입 등 지정한 부분만 바꾼다. 얼굴 전체를 다시 디자인하지 않는다.     |
| 개수 | 작은 발바닥 무늬 3개 ↔ 2개      | 무엇을 셀지 명확히 한다. 큰 발바닥 무늬와 다른 발은 유지한다.          |
| 모양 | 둥근 날개 끝 ↔ 각진 날개 끝     | 색·무늬·크기를 동시에 바꾸지 않는다.                                   |
| 무늬 | 체크 ↔ 줄무늬                   | 물체의 색 계열·윤곽·위치를 유지한다.                                   |
| 유무 | 구름 있음 ↔ 없음                | 없어진 쪽에서도 비교 위치와 판정 영역을 정할 수 있어야 한다.           |

한 게임에는 기본적으로 4개 이상의 유형을 넣는다. 한 유형은 정답 전체의 절반을 넘기지 않는다. 장면에 표정이나 셀 요소가 없으면 다른 유형으로 대체하고 이유를 계획에 기록한다. 개수를 맞추려고 장면과 무관한 차이를 억지로 넣지 않는다.

동물 쉬움 게임에서 적용한 혼합 배분 예시는 색깔 1개·표정 1개·개수 2개·모양 1개·무늬 1개·유무 1개다. 이 배분을 모든 게임에 그대로 복사할 필요는 없다. 반복 제작에서는 대상과 위치도 바꾼다.

## 3. 난이도 기준

| 난이도          | 정답 수 | 차이의 특징                                                                                       |
| --------------- | ------- | ------------------------------------------------------------------------------------------------- |
| 쉬움 (`easy`)   | 7개     | 비교할 대상이 분명하다. 사과 색, 입 표정, 발바닥 무늬 개수처럼 대상을 보고 차이를 판단할 수 있다. |
| 보통 (`medium`) | 8개     | 장면에 비교 대상이 더 많다. 여러 요소의 개수나 부분 무늬를 살피게 한다.                           |
| 어려움 (`hard`) | 10개    | 주변 묘사가 풍부하고 부분 구조·무늬의 차이를 더 꼼꼼히 비교하게 한다.                             |

쉬움도 색깔만 7개 바꾸는 방식으로 만들지 않는다. 어려움도 한두 픽셀, 흐릿한 색, 미세한 질감 잡음이나 좁은 판정 영역으로 만들지 않는다. 난이도는 비교할 내용과 장면의 복잡도로 조정한다. 손가락으로 선택할 수 있는 영역은 모든 난이도에서 확보한다.

## 4. 생성 전 계획

1. 원본을 실제로 보고 정답 대상이 구별되는지 확인한다.
2. 정확히 7·8·10개의 차이를 선정한다. 같은 물체의 서로 붙은 변경을 별도 정답 두 개로 쪼개지 않는다.
3. 각 차이에 ID, 유형, 원본 상태, 변경 상태, 좌우 예상 영역, 유지할 요소를 기록한다.
4. 유형 배분, 화면 내 분포, 영역 간 겹침을 점검한다.
5. 원본을 참조해 계획한 변경만 이미지 도구에 요청한다.

`plan.json`의 기록 예시다. `type`, `before`, `after`, `keep`은 제작 메모이며 배포용 `puzzle.json`의 필수 필드가 아니다. 예시 좌표는 해당 그림에서 다시 확인해야 한다.

```json
{
  "id": "animals-easy-new",
  "difficulty": "easy",
  "width": 1120,
  "height": 1400,
  "differences": [
    {
      "id": "difference-1",
      "type": "count",
      "description": "곰 왼쪽 발바닥의 작은 무늬 개수",
      "before": "작은 무늬 3개",
      "after": "가운데 작은 무늬를 지워 2개",
      "keep": "큰 무늬·발 윤곽·반대쪽 발 유지",
      "left": { "x": 0.337, "y": 0.66, "rx": 0.058, "ry": 0.043 },
      "right": { "x": 0.337, "y": 0.66, "rx": 0.058, "ry": 0.043 }
    }
  ]
}
```

실제 계획에는 난이도에 맞는 차이를 모두 기록한다. 결과를 본 뒤 계획에 없던 변경을 정답으로 추가해 개수를 맞추지 않는다.

## 5. 편집 요청 틀

아래 항목을 이미지 생성 요청에 포함한다. 현재 원본을 편집 대상으로 명시하고, 이전 변경 그림과 혼동하지 않게 한다.

```text
용도: 틀린그림찾기의 변경 그림 한 장.
참조: 원본 이미지. 원본과 동일한 비율·해상도·프레이밍 유지.
변경: 계획한 차이 N개를 각각 위치 / 원본 상태 / 변경 상태로 열거.
유지: 각 차이의 유지 요소와 나머지 사물·배치·크기·색·표정·조명·배경 유지.
금지: 계획 밖 변경, 전체 색감 변경, 물체 이동, 텍스트, 정답 원, 좌우 합성 출력.
출력: 변경 그림 한 장.
```

“더 다르게”, “더 어렵게”처럼 변경 대상을 지정하지 않은 요청을 피한다. 개수 차이는 제거할 요소와 남길 요소를 지정한다. 표정 차이는 바꿀 눈·입과 유지할 얼굴 요소를 지정한다.

이미지 생성과 의미가 바뀌는 편집은 Codex 내장 이미지 도구에서 수행한다. 코드로 사물을 그리거나 색을 바꾸지 않는다. 크기 정규화·포맷 변환·썸네일 제작은 코드로 처리할 수 있다. 정규화할 때 그림을 자르지 않는다.

## 6. 이미지 검수와 재작업

원본과 변경 그림을 나란히 보고 계획한 차이를 하나씩 확인한다. 그다음 계획한 영역 밖의 얼굴·손발·장식·배경·윤곽·색을 확인한다. 전체 보기와 확대 보기 모두 사용한다.

다음 중 하나라도 있으면 등록 전에 수정하거나 다시 생성한다.

- 계획한 차이가 없거나, 개수·표정 등이 계획과 다르게 생성됐다.
- 계획하지 않은 사물·표정·색·윤곽 변화가 별도의 정답처럼 보인다.
- 한 차이에서 색·모양·위치가 함께 바뀌어 여러 정답으로 보인다.
- 동일한 원본을 썼는데 구도·비율·배경 위치가 달라졌다.
- 차이가 너무 작거나 가려져 기본 비교 화면에서 대상 자체를 식별하기 어렵다.
- 정답 수를 맞추려고 의도하지 않은 변경을 끼워 넣어야 한다.

미세한 생성 질감 차이를 정답으로 취급하지 않는다. 다만 그 차이가 눈에 띄어 정답처럼 보이면 수정 대상이다. 자동 이미지 차이 계산만으로 시각 품질이나 정확한 정답 수를 보장하지 않는다.

수정할 때 원본과 성공한 이전 버전을 보존한다. `color-v1`, `shape-v2`, `mixed-v3`처럼 별도 제작 폴더에 이미지·계획·실제 프롬프트를 남긴다. 이미지 도구 오류는 동일 항목을 최대 한 번 재시도한다. 계속 실패하면 기록을 남기며 품질 기준을 낮춰 등록하지 않는다.

## 7. 정답 영역과 실제 플레이 검수

- 최종 이미지에서 좌표를 다시 확인한다. 예상 좌표를 그대로 확정하지 않는다.
- 좌우 영역은 각각 실제 차이를 감싼다. 지운 대상은 원래 있었던 위치를 사용한다.
- 영역이 이미지 밖으로 나가거나 다른 정답과 겹치지 않게 한다. 큰 주변 배경까지 과도하게 정답 처리하지 않는다.
- 발바닥 개수처럼 한 묶음의 차이는 묶음을 선택할 수 있게 한다. 사라진 작은 무늬 한 점만 눌러야 맞는 판정을 피한다.
- 양쪽에서 동일한 정답을 선택할 수 있어야 한다. 이미 찾은 차이를 다시 누르면 정답 수가 늘지 않아야 한다.
- iPad 가로 기본 보기에서 대상을 식별하고 손가락으로 선택할 수 있는지 확인한다. 세로·확대·힌트에서도 좌표를 확인한다.
- 힌트는 주변을 보여주고 자동으로 정답을 처리하지 않는다. 다시 풀기는 현재 게임만 초기화한다.

`content check`는 파일·크기·정답 수·좌표 범위를 검사한다. 브라우저 테스트는 주어진 좌표의 판정과 동작을 검사한다. 두 검사가 통과해도 그림의 내용이나 아이에게 적절한 난이도가 검증된 것은 아니다.

## 8. 등록과 품질 확인

제작 폴더에는 원본·변경 그림, 최종 `puzzle.json`, `metadata.json`, 썸네일, 차이 계획과 유형 배분, 실제 프롬프트, 검수용 이미지, 검증 결과와 미확인 사항을 남긴다. 제작자가 확인한 내용과 미확인 사항을 구분한다. 별도 부모 승인 단계는 두지 않는다.

`stage → review-image → content check → 로컬 플레이 검수` 순서로 준비한다. 공개 후보 교체는 기존 명령의 `--replace`와 보존 절차를 따른다. 명령과 JSON 계약은 [CONTENT.md](CONTENT.md)에 있다.

등록된 게임은 데이터 검사 후 모두 빌드에 포함한다. 승인 기록과 수동 검수 완료 플래그는 요구하지 않는다. 공개 배포는 사용자의 별도 지시가 있을 때만 수행한다. 보고에는 수정한 게임, 차이 구성, 검증한 내용, 확인하지 않은 내용, 로컬 게임 링크를 포함한다.
