# 그림콕콕 iPad 가로 모드 UI/UX 크리틱

가로 모드에는 **4:5 세로 구도 그림 두 장을 좌우로 배치하고, 놀이 상단을 한 줄로 합치는 방향**을 권한다. 폰트는 나눔스퀘어라운드 Regular·Bold를 우선 후보로 검토한다. 상단 축소만으로는 현재 3:2 그림이 충분히 커지지 않는다.

## 현재 화면의 판단

동화책 그림, 종이색, 숲색 글자와 노란 힌트는 제품의 정서에 맞는다. 양쪽 어디서든 정답을 누르고 두 그림을 함께 확대하는 구조도 비교 행동에 맞는다. 그러나 놀이 화면에 큰 브랜드 헤더, 제목 줄, 진행·도구 줄이 누적된다. 홈과 놀이가 같은 화면 밀도를 사용하는 것이 문제다. 홈은 그림을 고르는 책장으로 유지하고, 놀이에서는 비교 그림에 공간을 배분해야 한다.

현재 그림은 각 558×372 CSS px다. 두 그림의 면적은 1180×820 화면의 42.9%다. 검수 배너가 있을 때 그림 시작점은 y=269.8px다. 배너를 숨긴 모의 측정에서도 y=211px이다. 배너 때문에 더해지는 58.8px는 로컬 검수 화면의 비용이며 공개 화면 문제로 집계하지 않았다.

## 우선 문제

1. P1 — 가로 원본과 좌우 배치의 비율이 맞지 않는다. 현재 콘텐츠 18개는 모두 1536×1024다. 각 보드가 폭에 맞춘 3:2 비율이므로 상단을 줄여도 그림 높이는 그대로다. 새 게임에는 4:5 세로 구도를 우선 시험한다. 세로 구도에서 인물과 차이의 크기를 함께 설계해야 한다. 기존 그림을 잘라 쓰면 가장자리 정답이 사라지고 판정 좌표도 달라질 수 있다.
2. P1 — 놀이 상단에 중복 탐색과 세 줄의 제어가 있다. 브랜드 홈과 ‘다른 게임’은 같은 이동이다. 놀이에서는 뒤로가기·짧은 제목·진행·전체 보기·힌트·소리를 한 줄에 묶고 높이 64px를 먼저 시험한다. 조작 버튼은 48px 높이를 확보한다. 화면 폭이 부족할 때만 두 줄로 배치한다. 난이도는 홈 카드와 제목 옆 보조 정보로 두고, 상시 도움말은 처음 놀이 안내 또는 도움말 버튼으로 옮긴다. 자동으로 도구를 숨기지는 않는다.
3. P1 — 정답 판정 영역이 손가락에 너무 작은 게임이 있다. 558×372 보드에서 daily-hard-market의 ‘엄마 셔츠 왼쪽 위 단추 색’ 판정 영역은 4.464×4.464px다. animals-hard-bakery의 ‘작은 빵 잼 색’은 20.088×8.928px다. daily-easy-kitchen의 ‘머리끈 색’도 23.436×10.416px다. game.ts는 타원 내부만 정답으로 인정한다. 정답을 알아도 탭이 실패할 수 있다. 시각 표시와 입력 판정을 분리하고, 손가락 기준의 화면상 여유를 추가한다. 서로 가까운 정답의 판정 영역은 겹침과 오인정을 검수한다. 세로 구도로 바뀐다고 이 문제가 자동으로 해결되지는 않는다.
4. P2 — 한글 제목과 버튼에 실제 굵기 위계가 없다. Gowun Dodum은 400만 제공하지만 제목은 700을 요청한다. font-synthesis: none으로 굵기 합성도 막는다. 나눔스퀘어라운드 Regular·Bold를 UI 후보로 권한다. 버튼은 18px/Bold, 제목은 20~22px/Bold, 설명은 16px/Regular를 출발점으로 삼는다. Gowun Dodum은 로고와 짧은 놀이 문구에 남길 수 있다. 더 담백한 UI는 Pretendard 400·500·600이 대안이다. 외부 CDN 대신 자체 호스팅과 기존 오프라인 글꼴 캐시를 유지한다.
5. P2 — 도움말과 힌트의 표시 시점이 놀이 흐름에 맞지 않는다. 현재 도움말은 매번 화면에 남고, 힌트는 2초 뒤 사라진다. 초보 아이는 힌트 버튼에서 그림으로 시선을 옮기는 동안 표시를 놓칠 수 있다. 다음 그림 탭까지 유지하거나 4~5초 표시하는 안을 실제 놀이로 비교한다. 양쪽 그림 위 ‘첫 번째 그림/두 번째 그림’ 표시는 역할 구분에 비해 면적을 차지하므로 제거하거나 작은 바깥 표기로 바꾼다. 접근성 이름은 유지한다.

관련 개선 명령은 1·2에 impeccable adapt/layout/distill, 3에 impeccable harden, 4에 impeccable typeset, 5에 impeccable onboard/clarify다. 이번에는 크리틱만 수행했다.

## 비율 비교

계산 가정은 화면 1180×820, 바깥 여백 16px, 한 줄 상단 64px, 상단과 그림 사이 16px, 그림 사이 16px, 하단 여유 16px다. 사용 가능한 보드 박스는 각 566×708px다. 비율을 유지해 이 박스에 맞춘다. 제안값은 구현 후 측정값이 아니다.

| 구성 | 한 장 크기 | 두 그림의 화면 면적 |
|---|---:|---:|
| 현재 3:2 | 558×372 | 42.9% |
| 상단 축소 + 3:2 | 566×377 | 44.1% |
| 상단 축소 + 4:5 | 566×707.5 | 82.8% |
| 상단 축소 + 3:4 | 531×708 | 77.7% |

4:5는 높이를 쓰면서 그림 폭을 유지하기 좋다. 3:4도 개선되지만 더 좁아진다. 화면 높이를 720px로 줄이면 4:5는 486.4×608px이며 두 그림의 면적은 69.6%다. 따라서 83%를 모든 Safari 화면의 보장값으로 사용하면 안 된다. 이 값은 그림을 놓을 공간의 계산이며 실제 차이를 더 쉽게 찾는다는 증거는 아니다.

세로 기기 방향에서도 새 그림의 높이를 기준으로 배치해야 한다. 기존의 위아래 배치를 유지하면 세로 원본 두 장은 더 작아질 수 있다. 가로 모드의 개선과 세로 모드의 지원을 따로 확인한다.

## 유지할 부분

- 양쪽 그림의 동등한 크기, 동기 확대, 양쪽 정답·힌트 표시는 유지한다.
- 시간 제한과 감점 없이 진행을 보존하는 흐름은 유지한다.
- 노란 힌트, 글자가 있는 주요 도구, 체크 모양을 함께 사용하는 진행 표시는 유지한다.

## 사용자 관점

초보 아이는 차이를 발견한 뒤 작은 판정 영역에서 탭이 실패하거나 2초 힌트가 사라지는 순간에 막힐 수 있다. 손가락 사용자는 작은 차이를 찾기 위해 확대 조작을 반복해야 한다. Pencil 사용자는 화면 회전과 확대 후 좌표가 일치하는지 실제 기기에서 확인해야 한다. 이는 관찰된 플레이 결과가 아니라 코드와 화면에 근거한 검증 가설이다.

인지 부하 검사는 단일 집중, 시각 위계, 필요한 시점의 정보 공개가 약해 3/8 항목이 실패했다. 진행 숫자 7~10개는 선택지가 아니므로 선택 과부하로 집계하지 않았다. 놀이의 주요 도구 두 개도 선택 과부하는 아니다. 감정의 골은 ‘차이를 찾았지만 탭이 인정되지 않는 순간’이다. 완료 화면은 성취를 확인하는 끝점으로 유지한다.

## 구현 전에 확인할 제약

style.css의 aspect-ratio: 3/2와 Board.tsx의 데이터 기반 viewBox를 함께 수정해야 한다. SVG 박스와 그림 비율이 달라지면 빈 공간이 생긴다. 현재 판정·확대는 SVG 박스 전체를 기준으로 계산하므로, 세로 viewBox만 넣으면 정답 좌표가 어긋날 수 있다. 이미지 비율과 보드 박스를 일치시키거나 SVG 좌표로 정확히 변환해야 한다.

## 자동 검출과 시각 근거
